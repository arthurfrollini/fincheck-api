# AI Evals (part 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A 50-case categorization golden set, a keyless-tested harness (scoring, baseline gate, report), a runner that calls the real API through production code, and a nightly/dispatch `evals.yml`.

**Architecture:** `evals/` at repo root (out of the build, in jest `roots`). Pure libs in `evals/lib/`, the set and runner in `evals/categorization/`. The runner reuses `buildCategorizationRequest`, `LlmService.parse` and a new pure `interpretAnswer` extracted from `CategorizeTransactionService`.

**Tech Stack:** TypeScript, Jest 30, ts-node, zod 4, `@anthropic-ai/sdk`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-16-ai-evals-design.md`

## Global Constraints

- Golden set: exactly 50 cases, `source` ∈ `real | synthetic`, labels ∈ the 12 `DEFAULT_CATEGORIES` names + `none`, at least 3 INCOME cases.
- Gate: Haiku fails when `correct < baseline.correct - 2`. Other models are reported, never gated.
- Runner refuses a missing or `fake-` key before any call; no server-side fallback on eval calls; concurrency 5; per-case retry up to 3 with backoff on 429/5xx/network; more than 5 errored cases → run fails as `infra`, no baseline comparison.
- `evals.yml`: `schedule` 06:00 UTC + `workflow_dispatch` (input `models`, default `claude-haiku-5-5`). Never `pull_request`. Node 20. No DB services.
- Nothing in main CI calls the API.

## Review Focus

1. **Label/name mapping drift**: a golden-set label spelled differently from `DEFAULT_CATEGORIES` (`Alimentacao` vs `Alimentação`) must fail validation, not silently score as a miss. Test in Task 2.
2. **INCOME vs EXPENSE "Outro"**: two categories share the name `Outro`. Mapping a label to an id must use the case's `type`. Test in Task 4.
3. **All calls error** (bad key that isn't `fake-`, API down) must report `infra`, never update or fail against the baseline. Test in Task 4.
4. **`--update-baseline` with errors present** must refuse to write. Test in Task 4.
5. **Floor parity**: eval and production must agree on 0.49 / 0.5 / `none`. Covered by Task 1's shared function.

### Task 3: Scoring, baseline gate, report

**Files:** Create `evals/lib/score.ts`, `evals/lib/baseline.ts`, `evals/lib/report.ts` + `.spec.ts` each

**Interfaces:**
- `type CaseResult = { id: string; source: 'real' | 'synthetic'; expected: string; got: string | null; outcome: 'ok' | 'refusal' | 'max_tokens' | 'unparsed' | 'error'; costUsd: number; latencyMs: number }`. `got` is a category name, or `'none'`.
- `score(results: CaseResult[]): Score` with `{ correct, total, accuracy, bySource: Record<source, {correct,total}>, byExpected: Record<string, {correct,total}>, misses: CaseResult[], errors: number, costUsd, p50LatencyMs, p95LatencyMs }`.
- `compareToBaseline(score: Score, baseline: { correct: number; total: number } | undefined, tolerance = 2): { status: 'pass' | 'fail' | 'no-baseline'; message: string }`.
- `renderReport(model: string, score: Score, gate?: ReturnType<typeof compareToBaseline>): string` (markdown).

- [ ] Failing tests: accuracy and breakdowns on a 6-case hand-built set; an `error` case counts as a miss and in `errors`; percentiles. Baseline: equal → pass; −1, −2 → pass; −3 → fail and the message contains `-3`; +4 → pass, and the message suggests `--update-baseline`; undefined → `no-baseline`. Report contains the accuracy line, the by-source table and every miss.
- [ ] Run, expect FAIL.
- [ ] Implement.
- [ ] Run, expect PASS.
- [ ] Commit `feat(evals): add scoring, baseline gate and report`.

### Task 4: Runner + npm script

**Files:** Create `evals/categorization/run.ts`, `evals/categorization/runner.ts`, `evals/categorization/runner.spec.ts`; Create `evals/baselines/` (empty until the first real run); Modify `package.json` (`"eval:categorization": "ts-node -r tsconfig-paths/register evals/categorization/run.ts"`)

**Interfaces:** `runCategorizationEval(opts: { llm: Pick<LlmService, 'parse'>; model: LlmModel; cases: GoldenCase[]; concurrency?: number }): Promise<CaseResult[]>`. `run.ts` is the CLI (parses `--models`, `--out`, `--update-baseline`), builds a real `LlmService` without Nest (`createAnthropicClient`, `new LlmMetrics()`, a pino logger at `warn`), loops over models, writes `--out` JSON `{ models: { [model]: { score, gate } } }`, prints reports, and exits 1 on a Haiku `fail` or on `infra`.

Fixed category ids: one UUID per default category, `00000000-0000-4000-8000-0000000000NN`. Candidates per case = categories of the case's `type`. A `got` id maps back to a name through the same table.

- [ ] Failing tests (fake `llm.parse`): a correct answer → `got` = expected name; a `Outro` answer for an INCOME case resolves to INCOME's Outro, not EXPENSE's; confidence 0.4 → `got: 'none'`; refusal → outcome `refusal`, `got: null`; a 429 then success → retried, ok; 3× 500 → outcome `error`; requests use only same-type candidates and `buildCategorizationRequest`. CLI-level helpers: `shouldFailAsInfra(errors > 5)`; `--update-baseline` refuses when any case errored; refuses a `fake-` key.
